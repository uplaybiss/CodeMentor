# RAG Configuration Experiments

Empirical comparison of **embedding models** and **chunking strategies** for
EduAgent's retrieval-augmented generation (RAG) pipeline, measuring retrieval
quality and the latency each configuration adds.

The application is **never modified**: the experiment instantiates the real
`VectorStore` / `RAGService` classes and injects the embedding provider under
test — exactly how the production container wires them — and chunks documents
with either the application's own chunker or the alternative strategies in
[`chunkers.py`](chunkers.py).

## What is compared

**Embedding models** (first is the application baseline `all-MiniLM-L6-v2`):

| Model                         | Dim | Why included                                 |
|-------------------------------|-----|----------------------------------------------|
| `all-MiniLM-L6-v2`            | 384 | Application default (baseline)               |
| `multi-qa-MiniLM-L6-cos-v1`   | 384 | Retrieval-tuned variant of the same base     |
| `paraphrase-MiniLM-L6-v2`     | 384 | General semantic-similarity family           |
| `all-mpnet-base-v2`           | 768 | Quality flagship of the `all-*` family       |
| `BAAI/bge-small-en-v1.5`      | 384 | Modern, efficient retrieval model            |

**Chunking strategies** (first is the application default):

| Strategy | Description                              |
|----------|------------------------------------------|
| `baseline` | 600-token window, 100-token overlap  |
| `small`    | 300-token window, 50-token overlap   |
| `large`    | 1000-token window, 200-token overlap |
| `sentence` | Sentence-bounded chunks ≤ ~150 tokens (never splits a sentence) |

## How it is measured

For every (model × chunker) combination a fresh isolated ChromaDB store is
built and populated with a ground-truth five-topic corpus (generated by
[`make_corpus.py`](make_corpus.py)): photosynthesis, Newton's laws, cell
biology, electricity, and World War One. Each note is ~2,300–2,700 chars so
that every chunking strategy produces *several* chunks per document, making the
metrics discriminating. Sixteen queries are issued (3 per topic, plus 1
unrelated negative control that has no answer in the corpus) and scored per the
evaluation suite's M3 methodology:

- **hit@1** — expected source is the top-1 hit
- **precision@4** — fraction of top-4 hits from the expected source
- **recall@4** — expected source present in top-4
- **MRR** — reciprocal rank of the expected source
- **composite_quality** — mean of hit@1, precision@4, MRR (single 0-1 score)

Two latency figures are captured per configuration:

- **embed_s** — wall-clock to embed the whole corpus (ingest throughput)
- **query_s_mean** — mean wall-clock of one retrieval (query embedding + vector
  search) — the user-visible RAG latency attributable to the configuration.

> Note: full chat-turn latency is deliberately *not* compared here because the
> demo LLM provider dominates it and is configuration-independent. The latency
> numbers isolate the part of the pipeline this experiment can influence.

## Running

```bash
python experiments/run_experiments.py
```

The models are downloaded from HuggingFace on first run (a warm-up pass loads
them so downloads never pollute timing; an unavailable model is skipped, not
fatal). Models are compared on **retrieval quality** (higher is better) against
**query latency** (lower is better) — see the trade-off chart for the verdict.
